## 관찰 (LangSmith 트레이스로 교차 확인한 뒤 작성)

**표의 "유효 90%" 는 과대 보고다.** 스크립트의 사후 유효성은 `파일:줄` 이 존재하는지만 본다. 그래프의 validate 는 추가로 "read_code 로 읽은 범위 안인가" 를 검사하는데, 이 결과는 표에 없다. LangSmith 에서 20건의 validate 출력을 다시 읽어 집계한 **엄격 통과(최종 검증 오류 0 + 인용 1개 이상)는 13/20 = 65%** 다.

| 지표 | 표(사후) | 교차 확인(엄격) |
|---|---|---|
| 유효 | 90% | **65% (13/20)** |
| 도달(자동 근사) | 9/20 | 수동 보정 11/20 (rich-01 `console.py:1652 [print]` = Console.print, rich-04 `_calculate_column_widths` 는 실제 도달) |
| 비용 합 | $0.509 (단가 추정) | **$0.442** (LangSmith, 캐시 입력 할인) |

1. **실패 7건의 원인은 하나다: `read_code` 0회.** httpx-01·03·05, requests-05, click-04, rich-02·03 은 agent(gpt-4o-mini)가 find_definition/find_callees 만 11~15회 쓰고 코드를 한 번도 읽지 않았다. read_ranges 가 비어 "인용 가능한 범위: 없음" → 모든 인용이 "읽지 않은 코드" 로 거부 → 재작성 2회가 소용없음 → 2건(httpx-05, rich-03)은 인용 0개로 끝. **재작성이 발생한 7건 = read_code 0회 7건** 으로 정확히 일치한다. 재작성 비용($0.03 × 7)도 전부 여기서 나왔다.
2. 나머지 13건(read_code 1~5회)은 전부 엄격 통과. 09 의 단일 실행이 성공한 것은 운이 좋은 쪽이었다. **n=1 로 내린 "fast agent 가 끝까지 따라간다" 는 결론은 n=20 에서 65% 로 정정된다.** 측정 원칙 2·3(표본 크기 명시)이 왜 필요한지 보여 주는 사례.
3. **대응(기록 11)**: (a) 코드를 한 줄도 읽지 않은 채 답하려 하면 그래프가 "먼저 read_code 로 읽어라" 메시지를 넣어 agent 로 되돌림(넛지 1회, 지시가 아니라 흐름으로 강제). (b) 배치 스크립트가 read_code 횟수·최종 검증 오류·엄격 통과를 직접 기록해 표가 그래프 판정과 같게. 사후 유효성은 보조 지표로 내린다.
4. **상한 도달 10/20.** 도달 성공 11건 중 상한에 걸린 것도 있다(requests-01). 15회가 적정한지는 넛지 적용 후 다시 본다. 도구 평균 12.6회.
5. **def 줄 57% 는 이 과제에서 낮아도 괜찮다.** `Session.request:623/635/641` 처럼 함수 **안의** 줄을 단계마다 인용한 것은 따라가기 설명에 오히려 적합하다. `citation_at_def` 는 "정의 위치" 질문에 맞는 지표이고, 흐름 설명의 목표 지표가 아니다. 지표마다 적용 과제를 적어 둬야 한다.
6. 비용: 질문당 평균 $0.022(LangSmith), 시간 19.3s. 실패 7건을 빼면 평균 $0.020. 재작성이 없어지면 질문당 $0.02 아래.
